
# Store Package Guide

## Overview
DBアクセスの複雑なロジックを担当するパッケージ。  
`pkg/database`に用意された機能では実現できず、sqlを書いて機能を実現すべき時に実装する。  
特に複雑なSelect文のWHERE句を定義したり、複数テーブルのJOINを扱う。  
必要であれば、Web APIや特定フォーマットへのファイルアクセスなどI/Oを伴う操作もstoreに含める。  

## 資料
`docs/draft`配下の対応する集約のドキュメントを参照。  
store欄にsqlとともに定義されている。  
ドキュメントの読み方については、[docs/guideline/design.md](docs/guideline/design.md)を参照。  

## 実装基準
以下の条件を満たす場合は`pkg/database`の関数で実現できるため、storeの実装は不要。  
- 単一のテーブルにアクセスし、そのテーブルのカラムを素直にとってくるのみ
- 集計しない
- 対象のテーブルのカラムに対して、`col in () and ...`のようにin句のAND条件でのみ検索する
- 動的に検索条件を設定することはない  

どこまで可能なのかは正確に把握したい場合は、`pkg/database/core`に用意された関数を参照。  

## 実装
一つの関数につき、一つのファイルを用意する。  
関数名がファイル名となる。  

### オブジェクトとインターフェース
一つのファイルに、インターフェースとそれを実装する構造体の両方を定義する。  
構造体は`pkg/database/core#Executor`を拡張する形で定義し、メソッドを定義する形をとる。  
ファイル名は、`<集約>.go`、インターフェース名は、`<集約>Store`、構造体名は、インタフェースの頭文字を小文字とする。  

メソッドの内部で、関数を呼び出す。  
storeは同一の集約のbehaviorからしか呼ばれないため、`pkg/database/core#Executor`を拡張する際に競合を気にする必要はない。  

### モック
また、behaviorでモックできるように`mock.go`というファイルに、インターフェースを満たす形で実装する。  

### 関数定義
関数を定義し、それを構造体のメソッドから呼び出す形となる。  
関数名は、`Select<構造体名>By<Where条件>`の形式で命名する。

引数には、DB接続と検索条件を受け取る。  
戻り値は、coreの構造体のリストであることが多い。recordの場合もある。  

### SELECT実装パターン
例としては、以下のようなパターンがある。  

- 検索パターン
  動的にWHERE句を構築する検索機能の実装。  
  また、in句やequal以外での条件で検索する際も、storeに実装する。  
- 集計パターン
  特に集約ルートに対して無限長のリストが紐づく場合、全てをメモリにロードするわけには行かないので集計する。  
  集計する場合は、select定義がテーブルと一致しないので、`pkg/database`の機能が使えない。  

`docs/draft`配下のドキュメントでは`*`で表現されていたとしても、select句は`*`で指定するのではなく、必ず取得する項目をリストアップする形で、全てのカラムをselect句に記載する。  

## テスト
storeのテストは**必ずDBアクセスを伴う形**で実装する。mockは用意しない。

また、基本的に複数テーブルにJoinしていることが多いので、以下の両方のレコードパターンを用意する
- 関連レコードが存在するケース
- 関連レコードが存在しないケース（LEFT OUTER JOINの検証）

その他、where句やjoin句の条件パターンを満たすようにレコードを用意する。
