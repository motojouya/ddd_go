
# Design Guide

## Overview

設計においては、以下のドキュメントを用意する。
- docs/system.md
- docs/aggregate.md
- docs/draft/<date>_<aggregate_name>.md

## system.md
システム全体の構成を示す。主に以下の図を用意する。  

- システム構成図
  システム全体の構成を示す図。マルチシステムの全体概要となる。  
- ユースケース図
  マルチシステムを横断して、どのように使われるか。  
- DFD
  データフロー図。システム全体のデータの流れを示す。  
  システム構成図、ユースケース図よりも細かくなるので、ワークフローが分けられるのであれば、DFDも分割して定義する。  

全ての図はmermaidのgraphで記載できる。

## aggregate.md
全ての集約の関連を示すクラス図を記載する。また、全体にかかわる情報もここに記載する。  
また、複数の集約をまたがって形成するワークフローがある場合は、ワークフローのシナリオとしてシーケンス図を記載する。

メインはクラス図になるが、集約がクラスに対応する形。集約内のモデルをメンバー、集約のbehaviorが後悔する関数をメソッドとして記載する。集約間の関連も記載する。  
必ず記載すべきメソッドとして、集約境界を超えるものは必ず、記載する。
特に検索操作については、アプリケーションは超えないが、DBに投げるクエリは他集約のテーブルを参照するため、必ず記載する。  

## key.md
キーは複数種類が定義される場合もあるので、そのキーごとに以下の項目で解説する  

- 形式  
  キーの形式。単独か、複数で構成されるか。また文字列のフォーマット。独自型を定義するのであれば、その型  
- 利用  
  いつ定義すべきか。どう参照されるEntityで必要なのか  
- 発行  
  発行方法。発行する関数や、発行する関数を含めてEntityを作成できるutilityの定義など  

また重要な論点として、アプリケーションで発行するのか、DBのserialを利用するのか等も言及する  

## draft
各集約のクラス図でのモデリングと、実装の方針を記載する。  
ディレクトリ名の通り、コーディングが完了したら削除することを想定するドキュメント。  
逆説的に、draftディレクトリに書いた内容は、コードコメントを含めて、コードに反映されるべき内容である。  

### draft template
以下のフォーマットで記載する。  

- Lifecycle  
  どう特定するか？どう作るか？更新されるか？など、利用イメージを記載する。  
- Model
  mermaidのクラス図でモデリングする。  
  また集約ルートも記載するが、集約ルートには関連を記載しない。関連はcoreの項目に記載する。  
- Property
  クラス図では説明しきれない、各項目の詳細を記載する。
  - Description
  - Enum
  - Default
    デフォルト値。あるいは、idなどはどのように採番されるかなど。
- Note
  特記事項。ここまでがモデリングの情報であるが、以降はより実装に近い情報になる。
- Store
  関数ごとにsqlを定義する。動的に組み替える部分も含めて表現しておくこと
- Behavior
  behaviorの関数シグネチャを定義する、内部に保持するモデル(database,local)なども記載する。
  - Mutation
    更新系の処理の関数シグネチャを定義する。末尾に`{ create/update/delete/mutate <model> }`のように、集約内で実行するアクションと操作するモデルを記載する。
    アクションは`pkg/database/behavior`、あるいはcompany/warehouse_base等に定義されている手続きの定義を利用する
  - Query
    参照系の処理の関数シグネチャを定義する。末尾に`{ store.<関数名> / behavior.<関数名> }`のようにどのstoreかbehaviorの関数を呼び出すかを記載する。
    `behavior.<関数名>`については、ここ以外に定義がないが実装は必要。`store.<関数名>`は、Storeに定義がある。
  - Common
    内部で利用する共通関数を定義する。特に集約ルートから各要素を引っ張って関連付ける関数の定義は、どの集約においても必要。
- Controller
  エラー処理を除いたcontrollerの実装方針を記載する。他集約のbehaviorも呼び出すが、それらを網羅しておく
- WorkFlow
  想定される処理の流れ。統合テストのシナリオを記載するイメージ。

### Modelのクラス図

通常のクラス図にない要素として、core,entry,exitのどこに存在するべき項目か示しているものがある。  
項目の最も右側でに[]で囲まれた3文字のコード。ハイフンは対応する要素が存在しないことを示す。  

以下、凡例
- 1文字目: coreへの実装
  - p: primary key
  - u: unique key
  - m: 単なる項目
  - v: DBテーブルなどには存在しないが、計算されて出力される項目
  - e: 検索項目などstoreに渡すためにentryではなくcoreに実装される項目だが、外から入ってくるのでentryのようにtagにマッピングを記載する
- 2文字目: entryへの実装
  - c: contextとして入ってくる他の集約が持っている項目
  - i: inputとして入ってくる外部からの項目
  - l: 対応するcoreでは分けないが、entryでは単独の構造体になる項目。新規作成した後に別途追記する項目などが該当する。この項目だけの構造体を別途作成し、他とは分離する。
- 3文字目: exitへの実装
  - o: outputとして外部に出ていく項目
  - s: 項目としてはoutputの構造体に定義されるが、外部に出ることはない項目。tagで出力されないことが示される。

クラス図には、通常の構造体以外にも以下の構造体も定義する。
- 集約ルート  
  集約ごとに、単一の構造体で構成される集約は設けないこともあるが、構造体を関連させる際にルートが別なほうが都合がいいことも多い  
  集約ルートは、別の集約から参照されるため、最もシンプルな命名で`<集約名>`となることが多い。  
  その場合、実際に集約ルートとなってエンティティキーを持つ構想体は`集約名_root`となる。  
- 検索条件  
  いわゆるCriteriaに当たるもので、DBには保存されないが、他の構造体とは全く別で、入力値を得て、storeで利用されるためcoreに定義される。  
  命名は`<任意>_search`となる。  
- 依存対象のまとめ構造体
  クラス図上で別の集約への依存関係が示されているが、実際の更新の際に利用するときは依存しているものをまとめて利用する。  
  まとめるために用意するので、他の集約の集約ルートを持つ形。命名は`<任意>_depend`となる。  

## 設計ステップ
設計は基本的に、以下の順番でドリルダウンしていく。  
基本的に大枠から詳細に迫るわけだが、詳細の事情によって大枠の変更が必要になることもあるので、必要であれば前工程にフィードバックして修正する。  

- 1. システム全体設計  
  システムの利用イメージや全体像など。以下ドキュメントを作成する。  
  - docs/system.md
- 2. モデリング  
  システムで利用するデータモデリング。全体のaggregate.mdと詳細はdraft以下に。  
  draft以下のドキュメントは、他にも書き込むことがあるが、まずはLifecycle,Model,Property,Note項目の作成。  
  - docs/aggregate.md
  - docs/draft/<date>_<aggregate_name>.md
    - Lifecycle  
    - Model
    - Property
    - Note
- 3. 実装イメージ  
  モデリングと利用要求から導く、実装イメージ。かなり具体化されているがAIコーディングの制御のためのもの。  
  draft以下のドキュメントは、既に他の項目は記載されていて参考にするが、ここではStore,Behavior,Controller,WorkFlow項目の作成。  
  - docs/draft/<date>_<aggregate_name>.md
    - Model (集約ルート、検索条件、依存まとめなど)
    - Store
    - Behavior
    - Controller
    - WorkFlow
