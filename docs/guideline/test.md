
# Testing Guide

## Overview

以下の3種類のテストを用意する。
- 単体テスト IOなし
- 単体テスト IOあり
- 統合テスト

## 単体テスト IOなし
storeパッケージのモジュールは対象外。特定のファイル単体で完結するテストで、IOを伴わないもの。必要であればMockを利用する。  
テスト対象と同じディレクトリに配置し、`*_test.go`の命名規則に従う。パッケージは`<package>_test`とし、外部からの利用を想定したテストとする。  
また、Mockを利用する場合は、mockが呼ばれているか、mockに渡す引数が正しいかのチェックを行う。

その他のポイント
- トランザクション制御を伴うテストでは、`TransactionCalledCount`を使用してBegin/Commit/Rollbackの呼び出し回数を検証する
- controllerのコンストラクタは`NewXXXControl`を使用し、Mockを注入しておく
- 結果と期待値の比較には、`github.com/google/go-cmp/cmp`を利用する

## 単体テスト IOあり
storeのモジュールが対象。DBアクセスなどIOを伴うテストで、Mockは利用しない。  
基本的なルールはIOなしと同様で、ファイル名は`*_test.go`、パッケージ名は`<package>_test`。  
テスト用DBは、dockertestから利用する。`pkg/database/test`パッケージにこのためのヘルパーを用意している。  
また`pkg/company/store/mail_test.go`があり、こちらを対象ディレクトリにコピーすればそのままDBアクセスを伴うテストを実行できる。  

その他のポイント
- DBに登録するレコード、期待値のレコードは、テストごとに定義する。またレコードや期待値は複数のデータが必要だが、テーブルのように列そろえして定義する
  - テーブルのようにするので1レコードは1行で表現する
  - 列そろえするので、項目と項目の間に`/* */`を挟み、行内での項目の位置を揃えるように`*`の間のスペースの数で調整する
- テストケースは基本的に、レコードが全くない状態と、レコードがある状態の2つにする。通常の関数のテストは検査条件を絞るが、レコードのある状態のテストでほぼ全ての検査を行う点が違う
  - レコードが全くない状態は、取得結果が0件のケースとして
  - レコードがある状態のものはsqlの全ての条件を検査できるように様々なレコードを織り交ぜたDBの状態に対して行う
  - ただし、関数上で分岐がある場合は経路網羅できるように2より多いテストケースが必要。
- 結果と期待値の比較には、`github.com/google/go-cmp/cmp`を利用する。取得するデータ全てに対して検査すべきなため、特に必要。

## 統合テスト
特定のファイルではなく、アプリケーションを外から動かしてテストする。  
testディレクトリにyamlで定義し、runnを利用して実行する。  

`docs/draft`配下の対応する集約のドキュメントを参照。  
特にWorkflow欄に実装すべきシナリオが記載されている。
ドキュメントの読み方については、[docs/guildeline/design.md](docs/guildeline/design.md)を参照。  
ただし、複数集約にまたがってテストシナリオが構成される場合は、`docs/aggregate.md`にシーケンス図があり、それに沿ったテストとするので、その旨が`docs/draft`配下のドキュメントに記載されている。

ファイル構成
- `test/index.yml`: シナリオ全体のエントリーポイント。`init.yml` を最初に呼び、続けて集約単位のシナリオを順に include する
- `test/init.yml`: 全テーブルへの DELETE と基礎マスタ (company / worker / queue 等) の INSERT を行う
- `test/<aggregate>.yml`: 集約単位のシナリオファイル。集約ごとに別ファイルとし、`index.yml` から include する
- 共通の変数はindex.ymlに記載し、集約単位のシナリオファイルで参照する。各シナリオで得られた変数も再利用する場合はindex.ymlでbindする

`make runt port=<host port>` で実行する。app コンテナと postgres コンテナが起動済み・マイグレーション済みであることが前提。
